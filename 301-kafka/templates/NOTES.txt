[장애 원칙]

- Broker는 노드 + Local PV에 고정된다.
- 노드 장애 시 다른 노드로 자동 이동하지 않는다.
- 남은 Broker의 RF 복제로 서비스를 유지한다.
- 노드 교체/복구는 brokers 표를 수정하고 수동으로 진행한다.
- updateStrategy=OnDelete → 설정/이미지 변경 시 자동 재기동하지 않는다.
- 롤링 재기동은 Broker별로 상태를 확인하며 수동 진행한다.

[확인]

# StatefulSet / Pod
kubectl -n {{ .Values.global.namespace }} get sts {{ .Values.global.kafka.name }} -o wide
kubectl -n {{ .Values.global.namespace }} get pod -l app=kafka -o wide

# PVC / PV
kubectl -n {{ .Values.global.namespace }} get pvc -l app.kubernetes.io/part-of=data-layer
kubectl get pv -l app.kubernetes.io/name=kafka

# KRaft Quorum
kubectl -n {{ .Values.global.namespace }} exec {{ .Values.global.kafka.name }}-0 -- \
  /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:{{ .Values.global.kafka.ports.client }} \
  describe --status

# Topic
kubectl -n {{ .Values.global.namespace }} exec {{ .Values.global.kafka.name }}-0 -- \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:{{ .Values.global.kafka.ports.client }} \
  --list

# 운영 도구
kubectl -n {{ .Values.global.namespace }} rollout status \
  deploy/schema-registry deploy/kafka-ui deploy/kafka-exporter


[주의]

- 값 변경은 helm upgrade로 관리한다.
- bootstrap 주소는 global.kafka.brokers에서 자동 생성된다.
- 300-data-layer-base의 KAFKA_BOOTSTRAP도 같은 원본을 사용한다.
- Broker 추가/노드 교체는 global.kafka.brokers만 수정하고
  해당 노드에 kafka_prereq를 먼저 실행한다.
- helm uninstall 후에도 PVC와 Local PV의 실제 데이터는 Retain 정책으로 남는다.
